## 1. Recommendation: render public pages on the server

Use Next.js App Router for public pages, introduced route by route. Keep the existing Vite/React dashboard on its current subdomain. Today Vercel usually serves the same generic `index.html` for every public path; title, description, canonical URL, page body and metadata are filled in after browser JavaScript runs. The initial response lacks page-specific JSON-LD. Evidence: [Vercel routes](../../vercel.ts), [initial HTML](../../client/index.html), [client metadata helper](../../client/src/components/seo/MetaControl.tsx).

Reuse the current visual components and styles, shared types/validation, tRPC routers and services, Place URL authority, public eligibility checks and sitemap service. Move data loading and page metadata to the server; keep filters, enquiry forms, saved items and account controls interactive in client components. Metadata must use the same canonical URL and publication rules as the page. This is an incremental replacement, not a rewrite. See the [route-by-route inventory](public-page-rendering-inventory-2026-10-31.md) for current HTML, content, sitemap status and smallest fix.

Preserve existing canonical paths unless an approved redirect is required. Keep Sandton Place ID `pl-place-01-dee61758ef3bda7cd1a258ad` at `/gauteng/city-of-johannesburg/sandton`; show its exact Place listings as “Sandton Central.” Sandton Search Area is a separate guide. Broad Places such as Johannesburg and Pretoria guide buyers to exact suburbs and do not combine child listings. Keep Centurion’s Place ID `pl-place-01-1a30ae4d635ef747d6c987df`, change its preferred name from Lyttelton to Centurion only in the reviewed package, retain Lyttelton as an alias, and add a permanent 308 redirect from `/gauteng/lyttelton` to `/gauteng/centurion`.

**Effort:** 4–6 weeks for all nine public page types with one experienced engineer: about 3–4 weeks for home/search/Place/listing and another 1–2 for development and agent parity. ## 5. Phases, risks and independent review

1. **Validate hosting (about 1 week):** compare A and C in Preview/disposable capacity; check Vercel cpt1 function limits, Azure South Africa North API/worker SKU and quota, private database routing, pool behavior and per-query timing. Keep Plan B only as a short recovery bridge if service returns; caching does not fix cross-region database calls.
2. **Approve data (about 1 week):** founder checks exact existing Place IDs and Search Area members; record map-check Y/N and dated approval. Freeze the Place package once, then area membership as a separate artifact/digest. No guessed IDs, new Places or eligibility changes.
3. **Move public routes (about 3–5 weeks):** home/search/Place first, then listing, development and agent pages. Preserve dashboard, URL authority, eligibility and sitemap. Review every route in Preview.
4. **Prove engines and release (about 1–2 weeks, some overlap):** confirm independent server-side switches, email/enquiry/storage operations and human follow-up; run the full disposable rehearsal, then close B08–B18 with evidence. No production action is part of this memo.

Combined planning range: **6–9 weeks for one experienced engineer** if SSR and Railway replacement are sequential; **4–6 calendar weeks with two senior engineers** on separate workstreams is plausible, not committed. Risks: serverless database connection growth, duplicate SEO rules or bad redirects, provisional priority data, missing engine switches, worker delivery gaps, and unmeasured API/database paths.
