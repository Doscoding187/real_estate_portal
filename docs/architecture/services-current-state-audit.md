# Services Current-State Audit

**Status:** Architect audit deliverable (Services future-state mandate, Section 19)
**Basis:** Direct repository inspection on branch `slc/filter-ux-v2`, Database Authority v3
(`pnpm db:authority:status`: manifest-head-ready, schema-congruent, disposable-worktree target).

## 1. Verified audit hypotheses

| # | Hypothesis | Verdict | Evidence |
| --- | --- | --- | --- |
| A | Hard-coded taxonomy | **Confirmed** | `SERVICE_CATEGORY_VALUES` 6-value MySQL enum (`drizzle/schema/servicesEngine.ts:32`), duplicated as Zod enums in `server/servicesEngineRouter.ts:10`, duplicated again as TS union + display metadata in `client/src/features/services/catalog.ts:1`. Provider-created free text `service_code varchar(80)` sits beside the enum with no governance. Orphan generic `services` table also exists in `drizzle/schema/marketplace.ts:252` (only consumed by dead helpers `getAllServices`/`getServicesByCategory` in `server/db.ts`). |
| B | Request vs lead-assignment conflation | **Confirmed** | `serviceLeads` carries both `requesterUserId` and `providerId`; `createLeadFromContext` loops matched providers and inserts one row per provider (`server/services/servicesEngineService.ts:810-857`). The results page then creates *additional* lead rows per "Request quote" click (`client/src/pages/services/ServicesResultsPage.tsx:382`). No canonical request object exists anywhere. |
| C | Monetisation contaminates matching | **Confirmed** | `scoreProviderCandidate` adds `tierWeight(subscriptionTier)` (0/1/2) directly into organic relevance score (`servicesEngineService.ts:102-106,127`). Directory default order is opaque `trustScore` (default 50 for everyone). |
| D | Parallel provider/profile authority | **Confirmed** | `partners` (companyName, description, verificationStatus, trustScore, rating, reviewCount, logoUrl, websiteUrl, contactEmail, contactPhone) overlaps `service_provider_profiles` (websiteUrl, contactEmail, contactPhone, averageRating, reviewCount, moderationTier). Public profile query must coalesce both (`getProviderPublicProfile`). A third model, `explore_partners` (UUID string PKs, no FK integrity, JSON serviceLocations), duplicates identity/trust for Explore. Admin CRUD exists separately in `server/partnerRouter.ts`. |
| E | Parallel subscription authority | **Confirmed** | Four commercial authorities coexist: `service_provider_subscriptions` (tier/status enum, no money), `partner_subscriptions` (planId → billing.plans; used by founding-partner benefits), `partner_tiers` (ZAR price/features), and the canonical billing engine (`plans`, `planEntitlements`, `subscriptions`, invoices/payments). None of the first three carry real billing state machine value. |
| F | Geography divergence | **Confirmed** | `service_provider_locations.province/city/suburb` and `service_leads.geo_*` are varchar(120) free text matched by lowercased string comparison. Canonical geography authority (`provinces`, `cities`, `suburbs` with ids/slugs/placeIds/status in `drizzle/schema/locations.ts`) is unused by Services. |
| G | Trust model too generic | **Confirmed** | Three overlapping signals with no evidence model: `partners.verificationStatus` (pending/verified/rejected), `partners.trustScore` (decimal, default 50.00, assigned at signup, used in ranking), `service_provider_profiles.moderationTier` (basic/verified/pro — user-settable via router input!). `reviews.isVerified` flag has no linkage to any completed work. |
| H | Premature commercial assumptions | **Confirmed** | Onboarding spec Requirement 11 makes plan selection mandatory before go-live; `SubscriptionPlanStep.tsx` gates activation behind tier choice; `billingEligible`/`billingTierSnapshot` are written into demand rows at creation time. |

## 3. Additional findings

1. **`users.onboardingStep/onboardingComplete` mutation from services router** (`servicesEngineRouter.ts:122-136`) — a Services concern writing generic user onboarding columns on every status read; side-effect-in-query antipattern.
2. **`updateMyLeadStatus` permits arbitrary status jumps** (new → won) with no workflow guard; combined with per-provider rows this lets one provider mark a shared need "won" while others still hold it.
3. **`logLeadInteractionEvent` auth depends on string role comparison** and dedupes only `recommendations_shown`.
4. **`upsertProviderProfile` accepts `moderationTier` from the provider** — self-assigned trust tier.
5. **Session-storage dependency for request summary** (`readLeadContext`) — request facts live in sessionStorage, not the database.
6. **`foundingPartnerBenefitsManager` writes `partner_subscriptions`** — founding-partner program is a distinct domain; its coupling to the partner-subscription authority must be resolved in its own workstream before `partners*` retirement completes.
7. **No tests cover `createLeadFromContext` fan-out semantics**; existing frontend tests pin current UX (will be updated with UX rebuild).
8. **Schema inventory**: all v1 Services tables live in the immutable baseline migration `0000_canonical_launch_baseline.sql`; convergence therefore requires additive migrations + drops via the Database Change Protocol, never baseline edits.
